================================================================
  VARIANTS.txt — LAYOUT VARIANT LIBRARY + DESIGN KITS
================================================================
  Single source of truth for section layout skeletons, the
  design kits, and how the engine selects them. The variant
  ENGINE (src/lib/variants.mjs) reads this vocabulary; component
  files implement each named variant. Keep names here in sync
  with the component branches and the CATALOGUE in variants.mjs.


================================================================
  HOW SELECTION WORKS (read this first)
================================================================

  Selection is DETERMINISTIC, not live-random. variants.mjs
  seeds a PRNG from the business name + domain (or an explicit
  _brief.variantSeed). The same client always resolves to the
  same kit / variants / order on every build, forever. Different
  clients seed differently, so the portfolio looks varied.

  Per axis, the engine resolves in this order:
    1. Explicit value in _brief (designKit, layoutVariants[x]) —
       always wins.
    2. Filter the section's list by DATA PREREQUISITES (no photos
       -> drop photo variants; no stats -> drop stat-bar; etc.).
    3. Seeded random pick from whatever survives.

  Persisting picks: run  npm run variants  (scripts/pick-
  variants.mjs) to WRITE the resolved kit / variants / order into
  client-intake.json. It is idempotent — only empty slots get
  filled, and it never overwrites a value you set by hand. The
  site is already deterministic without it; persisting just makes
  the picks visible and editable.

  Reshuffle one client: set _brief.variantSeed to a new string
  and delete the picks you want re-rolled, then re-run.


================================================================
  NON-NEGOTIABLE RULES FOR EVERY VARIANT
================================================================

  - Tokens only. Use the semantic utilities backed by global.css:
    bg-bg, bg-card, bg-brand, bg-brand-dark, text-brand,
    text-accent, text-ink, text-muted, text-highlight, text-white,
    border-border, font-heading, font-body, rounded-card,
    shadow-card. Never hardcode hex. Never hardcode a font.
  - Colour comes from the CLIENT (style block, injected by
    Layout). Type/radius/shadow come from the KIT. A variant
    controls STRUCTURE only.
  - Container. Standard width is via the Container/Section
    primitives (max-w content / wide). Inner text keeps a
    readable measure even in wide/full-bleed layouts.
  - Vertical rhythm. Sections use py-16 lg:py-20 (Section default)
    unless noted. Heroes may go larger.
  - Mobile-first. Every multi-column layout collapses to ONE
    column below the lg breakpoint (1024px) — never md. This is
    what makes "half screen" stack cleanly.
  - Image fallback. Every <img> carries the error fallback:
      onerror="this.style.display='none';
      this.parentElement.classList.add('bg-gradient-to-br',
      'from-brand/20','to-brand-dark/30')"
    Photo-dependent variants are gated on features.hasPhotos so
    they are never auto-selected for a no-photo client.
  - Heading block. Optional eyebrow (class `section-eyebrow`
    + a colour utility only; size/weight/case come from
    global.css — sentence case, 15px, untracked, v3.22), heading
    (font-heading ... text-brand), optional subhead (text-muted).
    Running text never exceeds 40em (global measure rule).
  - No new dependencies. Carousels/accordions/rotators use
    vanilla JS or CSS only.


================================================================
  DESIGN KITS  (axis 1 — picked once per site)
================================================================
  A kit bundles TYPE + RADIUS + SHADOW + RHYTHM personality. It
  does NOT set colour. Defined as .kit-* classes in global.css;
  Layout adds the class to <html> and loads the kit's fonts.

  ledger   — editorial/journalistic. Newsreader + Public Sans.
             small radius, hairline shadow, tight tracking.
  workshop — industrial trade. Archivo (heavy) + Public Sans.
             square radius, hard offset shadow.
  coast    — soft/approachable. Archivo + Source Sans 3.
             large radius, diffuse shadow, airy.
  press    — classic/refined. Fraunces + DM Sans.
             small radius, light shadow, loose rhythm.
  signal   — modern. Bricolage Grotesque + DM Sans.
             medium radius, minimal shadow.

  Override per client: _brief.designKit: "press".

  v3.28: NO KIT LOADS INTER OR SPACE GROTESK. They are the two
  faces a generated site reaches for first (DESIGN-LIBRARY B14).
  The faces above are what the code loads: KIT_FONT_FACES in
  src/lib/variants.mjs is the source of truth, and this list had
  drifted from it on coast and press. To change one client's
  type, set _brief.stylePicks (it overrides the kit).


================================================================
  SECTION ORDER  (axis 2 — picked once per site)
================================================================
  Pinned near the TOP: hero, then services.
  Pinned to the BOTTOM: faq/faqs, then contact.
  Everything else (story, whyUs, tiers, usage, testimonials) is
  seeded-shuffled in the MIDDLE. Order is derived from the
  intake `sections` array; sections not listed do not render.


================================================================
  HERO   (axis 3 — per-section variant)
================================================================
  Reads `hero`: eyebrow, heading, subhead, body,
  primaryCtaLabel/Href, secondaryCtaLabel/Href, trustMarks[],
  image (optional).

  typographic  [DEFAULT]  Left-aligned oversized H1, subhead as
    a lighter continuation, body at readable width, CTA row,
    inline trust marks, one understated motif. No photo.
  split-media  [needs photos]  Content left, media right, equal
    columns; image object-cover rounded-card. Stacks on mobile.
  fullbleed    [needs photos]  Full-viewport background image with
    a brand-dark scrim, white text. Falls back to solid bg-brand
    if no image.
  docket       [needs 4+ spec rows]  Copy left, ruled spec panel
    right — services, areas, hours, licence/ABN, established.
    Every row is sourced from the intake; a row with no value is
    omitted, never filled with "Contact us". Needs four resolved
    rows (v3.34): with three, the panel is half the height of the
    copy and the right column reads as empty. Short of four, the
    engine skips it and a forced docket renders the index hero
    (4+ services) or typographic instead.
  index        [needs 4+ services]  Numbered service index on a
    tinted rail, copy right. Puts the service list above the
    fold. The ordinals are an INDEX, not a sequence — no rail,
    no connectors, no arrows between them.
  stat-lede    [needs hero.stats]  Oversized figure leads,
    headline beside it, remaining stats in a ruled strip below.
    ABSORBS the HeroStats strip, which is suppressed while this
    variant is active. No placeholder state: no real stat, no
    variant.


================================================================
  SERVICES
================================================================
  Reads `services`: eyebrow, heading, subhead, items[] (title,
  description, longDescription, includes[], price, href,
  image, imageAlt, featured).

  Per-service images are gated on features.hasPhotos as well as
  a path — a per-service photo asserts the client did THAT job.
  The hero image is not gated this way; see content.mjs.

  grid-icons   [DEFAULT, no assets]  ONE RULED SHEET (v3.28), not
    separate cards: icon or ordinal + title + description + up to
    4 includes per cell, the cells sharing one frame and one
    hairline between neighbours. The grid WRAPS; its column count
    is sized for the services, and the last service runs to the
    end of its row so no count leaves an empty cell. The quote
    action closes the sheet as a FULL-WIDTH ACCENT ROW (label +
    the phone, or opening hours on a call-first site). It is no
    longer a service-shaped card, and it never prints the phone
    number twice. services.showQuoteCard:false removes the row.
    A real service is never dropped to make a row even.
  ledger       [no assets]  Ruled rows, title left / description
    right / optional "from" price. No cards. Handles very uneven
    description lengths, which is where card grids break. The
    price column disappears entirely when no service carries a
    price — never padded with "POA".
  split-scroll      [needs a photo on MOST shown items: 2/3, v3.17]  Alternating
    full-width image/text rows, media side flips each PHOTO row on
    desktop. Text always leads on mobile. A service without a photo
    runs as a full-width text row (copy left, inclusions + quote
    link right) — v3.20; it used to leave an empty grey panel.
  feature-lead [needs a photo on the LEAD service]  One large
    service card with imagery, the rest stacked beside it in a
    single bordered group. Lead comes from items[].featured —
    first true wins, otherwise items[0].
  list-detail  [needs longDescription + 2 includes on EVERY
    service]  Nav list drives a detail panel on desktop,
    accordion below. Renders as a working accordion with
    JavaScript off.

================================================================
  SERVICES PAGE   (MANUAL axis — /services layout, v3.19)
================================================================
  Reads `services.page` (eyebrow, heading, subhead, quoteHeading,
  quoteBody, featuredHeading, moreHeading, midHeading, midBody),
  `services.groups[]` ({ id, heading, intro, image, imageAlt }) and
  `services.items[]` (+ group, anchor). Built by
  resolveServicesPage in src/lib/content.mjs.

  MANUAL: the seeded engine NEVER picks this. Set
  _brief.layoutVariants.servicesPage by hand; unset = stacked. It
  consumes no RNG, so it shifted nothing for built clients.

  Shared by all four: the page H1 block, and a full-bleed accent
  quote band (keyworded H2, quote + phone buttons) closing the page.
  Every service's longDescription is in the HTML in every variant.
  Every service has an anchor (items[].anchor or its title
  slugified) so /services#<anchor> deep-links to it.

  stacked   [DEFAULT, no prerequisite]  One service per row, rule
    between rows. Photo rows split text/photo and alternate; rows
    without a photo run full width as two text columns, never half
    empty. Best at 1-6 services.
  grouped   [needs services.groups + items[].group]  Jump chips,
    then per group a sticky rail (number, H2 group heading, intro,
    photo, quote button) beside a 2-column card grid. Needs one photo
    per GROUP (borrowed from its first photographed item if unset).
    Without groups it degrades to one 3-column card grid. Best at
    8-20 services across 2-4 kinds of work.
  featured  [works best with 3-6 photos]  Photo cards for the
    headline services (featured:true + photo, else every photo,
    max 6), a full-bleed dark quote band, then a 3-column catalogue
    of the rest with "Details" disclosures. Odd counts give the lead
    card a double span so the grid has no hole. Best at 7-14.
  index     [no prerequisite]  Desktop: grouped service list left,
    one service in full right. Below 1024px: grouped accordion. Deep
    links open the right service. No-JS renders every service in
    full. Best at 10+ services where people arrive looking for one
    specific job.

================================================================
  WHY US
================================================================
  Reads `whyUs` (array of title, description) or {heading,
  items[], trust[], type, pairs[], themLabel, usLabel}.

  ALL FOUR RENDER INSIDE THE DARK BAND. whyUs is the template's
  only permanent mid-page inverted section and the engine relies
  on it — whyUs and its immediate neighbours are excluded from
  BAND_ELIGIBLE. A light whyUs variant would invalidate that for
  every existing client, so the band engine has to change in the
  same commit if one is ever wanted.

  ruled-rows    [DEFAULT]  Hairline rows, title left / desc
    right. NO NUMBERING — the points are not a sequence and can
    be reordered without losing meaning.
  icon-grid     Ruled checklist (v3.28): a hanging tick, the title
    and its sentence on one left edge, a hairline above each
    entry. NO boxes and NO tick-in-a-circle badge (DESIGN-LIBRARY
    B10). Column count is chosen to divide the item count, so the
    last row is never left with a hole.
  contrast-pair [needs whyUs.pairs[]]  Two columns, the shortcut
    vs what we do, x against tick. Names the competitor's corner
    cut without naming a competitor. Reads a DIFFERENT shape
    from items[] and is filtered out without it — the "them"
    column is not derivable from a list of benefits and must
    never be invented.
  process-rail  [needs whyUs.type: "process"]  Numbered steps on
    a connecting rail, capped at five so the sequence never
    wraps on desktop. THE ONLY VARIANT THAT ASSERTS AN ORDER.
    The test is whether the items can be reordered without
    losing meaning; if they can, this variant is wrong for them.
    Gated on the intake declaring a process, never inferred.

================================================================
  STORY
================================================================
  Reads `story`: eyebrow, heading, body, image, imageAlt, cards[],
  process[]. credentials-panel also reads business.licence / abn /
  established / insurance / memberships[].

  The heading block and the numbered process strip are SHARED by all
  three variants; only the body between them changes.

  ruled-cards       [DEFAULT, no assets]  Copy first (v3.28): the
    first paragraph as a lede on the left, the rest of the copy
    beside it, then story.cards as ONE RULED STRIP: a rule above,
    hairlines between entries, no boxes. One paragraph runs as a
    single lede at the reading measure. Still the fallback for the
    other two variants. (Before v3.28 this was three bordered cards
    ABOVE the copy. credentials-panel prints the same strip under
    its split.)
  credentials-panel [needs 2+ resolved credential rows]  Copy left,
    ruled spec panel right: licence, ABN, established, insurance,
    memberships. Same grammar as hero/docket. EVERY ROW IS SOURCED —
    a field with no value is omitted, never filled with "Contact
    us". Under two resolved rows the panel drops and the copy runs
    full width, because a one-row panel reads as a mistake. Rows come
    from resolveStoryCredentials in src/lib/content.mjs, the same
    function the engine gates on, so the gate and the render cannot
    disagree.
  portrait-lede     [needs features.hasPhotos AND story.image]
    Operator portrait left, copy right, cards as a ruled pair-grid
    beneath the copy. The frame holds a fixed ratio at every width
    (4:5 phone, 3:2 tablet, 3:4 desktop) so it reserves its space
    before the file loads and never collapses if it does not.

================================================================
  AREAS
================================================================
  Reads `usage`: eyebrow, heading, subhead, areasLine, travelLine,
  notCoveredLine, featured[], items[], zones[]. The directory also
  reads `serviceAreas` through collectAreas/buildableAreas in
  src/lib/areas.mjs, so the homepage index and /areas can never
  disagree about what is covered.

  This is the HOMEPAGE summary. The full suburb list on /areas is
  handled by Usage.astro and has no variant axis. /areas is off by
  default in PAGE_DEFAULTS, so the homepage section is the half
  that ships on a basic build.

  NEVER INVENTS a radius, a travel fee, a zone or a suburb.

  chips      [DEFAULT, no prerequisite]  Head left, coverage line
    and the suburbs right. v3.28: the suburbs are a LINE OF PLACE
    NAMES divided by hairlines, not outlined pill chips (zoned sets
    its suburbs the same way, and so does /areas). The variant
    keeps its name; usage.areaStyle: "pills" restores the chips
    for a client who wants them. Still the fallback.
  zoned      [needs 2+ real usage.zones]  One ruled block per zone:
    name left, that zone's suburbs right, optional per-zone
    travelNote beneath. A zone counts only if it is NAMED and holds
    at least one suburb; one zone is a heading, not a grouping,
    hence the floor of two. Zones are read from the intake and are
    NEVER derived from suburb names — deciding that Reynella is
    "southern" is a coverage claim the client did not make.
    Suburbs listed but not placed in a zone render last WITHOUT a
    label; they are never swept into an invented "Other" zone.
  directory  [needs 12+ collected areas; renders 6]  Alphabetical ruled index,
    2 columns at 40rem and 3 at 64rem. A suburb that clears
    areaPageState becomes a link to /areas/<slug>; one that does not
    renders as plain text, never as a dead link. Uses CSS
    column-count rather than a grid (unlike faqs/open-columns):
    each entry is one short line with no pair to split, and column
    flow reads top-to-bottom, which is how an index is scanned.
    Below a dozen suburbs a chip row is shorter and friendlier;
    past a dozen the chip wall becomes a blob.

================================================================
  FAQS
================================================================
  Reads `faqs`: eyebrow, heading, items[{question, answer, group?}].
  An item missing a question or an answer is DROPPED, not rendered
  as an empty row. The FAQPage JSON-LD in Layout.astro is emitted
  for all three variants and is unaffected by the choice.

  Rendered by ONE component in two places: as a homepage section,
  and by /faq with headingLevel="h1". The page no longer carries
  its own copy of the markup.

  accordion     [DEFAULT, no prerequisite]  Head left, <details>
    list right. The original layout, renamed only.
  open-columns  [needs 6+ complete items]  Every answer printed
    open across two tracks at lg, one below. Uses a two-track GRID,
    not CSS `column-count`, which can split a question from its
    answer across the gutter. Better surface for assistants that
    read the page rather than the JSON-LD; below six questions it
    reads as a layout that ran out of content, hence the gate.
  grouped       [needs 2+ distinct item.group values]  One ruled
    block per category, label left, questions right. One group is
    not a grouping, so the floor is two. Questions with no group
    render last WITHOUT a label — they are never invented into an
    "Other" bucket, same rule as an unsourced credential row.

================================================================
  SECTIONS WITH ONE LAYOUT  (no variant axis; revised v3.28)
================================================================
  TESTIMONIALS  A scrollable row of REVIEW CARDS, set the way the
    review platforms set them: initial, name, platform mark
    (Google or Facebook, linked to the source), stars only when
    the item states a rating, then the text. Three or fewer share
    one row; more than three scroll sideways with scroll-snap,
    previous / next buttons on desktop and keyboard scrolling. A
    long review is clamped to seven lines with "Read more" (JS
    only, so no-JS prints it in full). The head carries a link to
    the review profile and, ONLY when testimonials.rating states
    it, the profile's score and count. Nothing is invented: no
    rating in the intake means no stars. Sits on the tint
    surface. Order matters: the first three show before scrolling.
  GALLERY (homepage)  Mosaic. The first image leads at 2x2 and
    the rest sit around it at a tight gap; every count from 1 to 6
    has a shape with no hole (1 wide, 2 halves, 3 lead+2, 4 2x2,
    5 lead+4, 6 lead+2+3). Two columns on a phone, lead full
    width. The author picks the lead by ORDER.
  CONTACT  The form has no box: its fields sit on the section's
    left edge with a 3:1 field boundary. The details panel beside
    it keeps the band surface. With no form endpoint the phone
    number is set at display size and the panel drops the rows the
    left column already says.
  FOOTER  footer.columns wins when filled. Left empty, the link
    columns are DERIVED: "Services" from services.items (deep
    links to /services#anchor when that page is built) and "On
    this site" from the header nav. Never invented.
  HERO / HEADER  One call action each. When the CTA is a tel:
    link, the plain "Call 04xx" text link beside it is dropped.

  HEADER

  standard [DEFAULT]  Logo left, nav links, phone + CTA right.
  minimal             Logo + single phone CTA; no link list.
  centered            Stacked centred logo + links, CTA right.

================================================================
  ADDING A NEW VARIANT
================================================================
  1. Add the name to the section's list in CATALOGUE
     (src/lib/variants.mjs).
  2. If it needs data, add a "section/variant" entry to PREREQS.
  3. Implement the branch in the component, tokens only.
  4. Document it here. Never introduce a dependency or hex.

================================================================
  SURFACE  (axis — page background treatment, one per site)
================================================================
  Seeded per site (or _brief.surface). Subtle + colour-safe; applied to
  --c-bg only when the client has NOT set an explicit style.bg.

  flat  [default feel]  No change; the paper --c-bg as-is.
  tint  Page washed in the brand-50 ramp step (derived in Layout).
  warm  Neutral warm paper (#faf7f2) regardless of brand.

  Override: _brief.surface: "flat" | "tint" | "warm".


================================================================
  SECTION-HEAD GRAMMAR  (kit-driven, NOT a per-section variant)
================================================================
  Every section head carries two hook classes: .section-eyebrow and
  .section-heading. The treatment is chosen by the ACTIVE KIT (class on
  <html>), so it is consistent across all sections of one site and varies
  between clients with the kit. Defined in global.css. There is nothing to
  set per client — it follows the kit.

  v3.22: every kit's eyebrow is sentence case, 15px, untracked — no
  caps, side bars, lead rules or prefixes (impeccable flags all four).
  Kits vary it by face, weight, style and colour only:
  ledger    italic, medium weight.
  workshop  heading face, bold.
  coast     highlight colour.
  press     italic, highlight colour; larger serif heading.
  signal    medium weight.


================================================================
  COLOUR BAND  (axis — one dark mid-page section, contrast-gated)
================================================================
  The engine picks ONE eligible mid section to invert into a dark brand
  band (bandSection). Eligible: tiers, usage, whyUs, story, testimonials
  (only Section.astro-based sections, so the token remap flips cleanly).
  Hero/Services/FAQ/Contact never band.

  Mechanism: the assembler wraps the chosen section in .band-dark, which
  REMAPS the semantic colour tokens (--color-*). Every component inside
  flips to white-on-dark automatically — no per-component edits.

  Contrast guard: a band only appears if WCAG relative luminance of the
  client's dark brand is <= 0.183 (white text clears ~4.5:1). Light-branded
  clients get NO band rather than white-on-pale.

  Override: _brief.bandSection: "none" (disable) | a section key (force).

  One style per site. Placed by the assembler between adjacent content
  sections; skipped after the hero and around the colour band.

  none      rely on background alternation only.
